
本文档是一个 AI Skill 的完整规范，供模型实现时参考。

**Skill 的作用**：当用户提供"业务需求"和"基线 PRD"后，Skill 自动完成影响域分析，输出结构化的改动方案和可执行的 Story 供用户确认，用户审查、修改、批准后产生增量 PRD 文档。

---

## 一、为什么需要这个 Skill（Why）

### 1.1 问题背景

企业 IT 系统在持续迭代优化过程中，每次业务提出新需求，都要回答同一批问题：

- 这个需求影响哪些 PRD 设计要素？
- 哪些要素需要改，改什么？
- 哪些地方绝对不能动？
- 开发怎么拆 Story，怎么验收？

这些问题有规律可循，但如果靠人逐次手动分析，效率低、容易遗漏、结论不一致。

### 1.2 Skill 解决的核心问题

**问题一：影响域不清**
业务说"加一个按钮"，实际上可能影响应用架构、UI 原型、信息架构、功能特性、权限设计等多个 PRD 要素，且这些要素之间存在上下游依赖关系，改了 A 必须同步检查 B。人工分析容易只看到直接影响，漏掉传导影响。

**问题二：改动范围不可控**
在 Coding Agent 参与开发的场景下，如果没有明确的任务边界和禁止项，Agent 可能在分析中自行扩展改动范围，改到不该改的地方。

**问题三：验收标准不可执行**
传统 PRD 的验收标准是给人读的描述，无法直接转化为测试用例，也无法让 Agent 自我核查。

### 1.3 Skill 的价值

通过结构化分析，把"一段业务需求文字"转化成"精确的改动点 + 禁止项 + 可执行的验收标准"，让人只需要做最终确认，而不是从零分析。

## 二、整体流程（What）

### 2.1 Skill 的角色定位

```
【输入】
  （A）业务需求 / 业务方案（用户提供）
  基线 PRD（用户提供）

      ↓

【AI Skill 执行，遇到证据不足时立即暂停询问，不猜测】
  Step 1：解析业务需求，识别（B）原子变化场景
  Step 2：通过映射规则，推导（C）主触发 PRD 要素
  Step 3：通过依赖传导规则，推导（D）次要影响要素
  Step 4：对照基线 PRD，确认（E）要素改动点，识别禁止改动项
  Step 5：（F）面向实施，拆分增量 Story，编写结构化验收标准

      ↓

【输出草案，等待人工确认】
  改动点 + 禁止改动项清单 + Story 及验收标准清单

      ↓

【人工确认】
  用户审查、修改、批准

      ↓

【输出】
  增量 PRD 文档
```

分层说明：

- **（A）业务需求 / 业务方案**：输入层，回答"为什么要改、业务想解决什么问题"。
- **（B）原子变化场景**：入口层，回答"产品上到底变了什么"。
- **设计要素层**：承接层，回答"哪些 PRD 章节需要变化"。其中又分两类：
  - **（C）主触发 PRD 要素**：原子场景直接命中的要素。
  - **（D）次要影响要素**：因 PRD 要素间的上下游依赖关系被间接触发的要素。
- **（E）要素改动点**：设计层，回答"每个章节具体怎么改，以及哪些不能改"。
- **（F）面向实施**：收口层，回答"开发怎么落地、验收怎么验证"。

### 2.2 人做什么、AI 做什么

| 环节 | 执行者 | 内容 |
|---|---|---|
| 提供业务需求 | 人 | 业务需求文字、业务方案说明，以及分析过程中的细节澄清 |
| 提供基线 PRD | 人 | 当前系统的完整 PRD 文档 |
| Step 1~5 分析 | AI Skill | 原子场景识别、要素推导、改动点/禁止项分析、Story 拆分/AC 编写 |
| 审查草案 | 人 | 检查分析是否准确、是否有遗漏或错误 |
| 确认 / 修改 / 批准 | 人 | 对结果负责的节点 |
| 增量 PRD 文档 | AI Skill | 按确认结论结构化输出 |

## 三、两条铁律

这两条规则优先级高于一切，在执行任何 Step 时均须严格遵守。

### 铁律一：有理有据，不猜测

**每一条分析结论都必须有明确的依据来源。** 依据只有两种：

- **来自业务需求原文**：直接引用原文片段作为证据
- **来自基线 PRD**：明确指出基线 PRD 的章节名、表格行或字段名

**当依据不足时，唯一合法的处理方式是：暂停并询问用户，而不是推断或假设。**

具体表现：
- 业务需求描述了"录入供应商信息"，但没说具体录哪些字段 → 不能自行推断字段，必须询问
- 基线 PRD 的权限矩阵章节缺失 → 不能假设权限规则，必须询问
- 需求中提到"历史数据需要处理"，但没说怎么处理 → 不能自行设计迁移策略，必须询问

### 铁律二：随时暂停，主动澄清

**分析过程不是一次性的线性执行，而是允许在任何步骤中途暂停询问。** 以下情况必须暂停：

| 触发情形 | 暂停时机 | 示例 |
|---|---|---|
| 业务需求有歧义，同一段描述可以对应多个不同的原子场景 | Step 1 识别时 | "优化供应商选择"——是新增页面、还是现有页面加字段，无法判断 |
| 原子场景识别置信度为"低" | Step 1 识别后 | 需求只说"改善体验"，没有具体操作描述 |
| "需验证"要素在基线 PRD 中找不到对应章节 | Step 2/3 推导时 | 基线 PRD 无权限设计章节，无法判断是否影响权限 |
| 改动点的 target_state 无法从需求中确定 | Step 4 分析时 | 需求说"加字段"但没说字段名、类型、必填性 |
| 历史数据处理策略不明确 | Step 4 分析时 | 需求未说明存量数据如何处理 |
| 禁止改动项依赖外部系统知识，PRD 中无记录 | Step 4 分析时 | 某接口是否有外部调用方，PRD 中未标注 |
| 基线 PRD 中存在相互矛盾的内容 | 任意步骤 | 功能特性描述和信息架构字段定义不一致 |

**暂停和询问的格式要求**：

```
⏸ 分析暂停 — 需要澄清以下问题，才能继续执行 [Step X / 要素名]：

Q1：[具体问题]
背景：[为什么需要这个信息，不澄清会导致什么无法判断]

Q2：[具体问题]
背景：[为什么需要这个信息]

请回答以上问题后，我将继续分析。
```

**要求**：
- 同一次暂停中的问题必须集中一次性提出，不要逐问逐答（太碎片化）
- 每个问题必须说明"背景"，让用户理解为什么这个问题是必须回答的
- 问题应具体，不能是泛化的"请补充更多信息"
- 收到回答后，从暂停的步骤继续执行，并在输出中注明"根据用户澄清：[关键信息]"

## 四、关键概念定义（What）

Skill 执行过程中会产生以下结构化对象，实现时严格按这些格式输出。

### 4.1 原子变化场景（AtomicScenario）

```
AtomicScenario = {
  id:            场景编号（如 UI-01）,
  name:          场景名称,
  evidence:      从需求原文中提取的依据（直接引用原文片段，不能改写）,
  confidence:    高 / 中 / 低（识别置信度）,
  open_question: 置信度为中/低时的待确认问题（置信度高时可空）
}
```

### 4.2 改动点（ChangePoint）

```
ChangePoint = {
  id:              改动点编号（如 CP-001）,
  source_scenario: 来源原子场景编号,
  trigger_type:    主触发 / 依赖传导（注明传导规则编号，如 T-01）,
  element:         受影响的 PRD 要素名称,
  action:          新增 / 修改 / 删除 / 复用 / 不涉及,
  baseline_ref:    基线 PRD 对应章节名或内容（必须精确引用，不能空缺）,
  baseline_state:  基线现状描述（直接引用基线内容，或说明"基线无此内容"）,
  target_state:    变更后目标状态描述（必须有需求原文或澄清回答作为依据）,
  in_scope:        本改动明确包含的对象列表,
  out_of_scope:    本改动明确排除的对象列表
}
```

### 4.3 禁止改动项（ForbiddenItem）

禁止改动项是独立列表，与改动点并列输出，不内嵌在 ChangePoint 中。

```
ForbiddenItem = {
  id:           禁止项编号（如 FB-001）,
  target:       禁止改动的具体对象（实体名 / 字段名 / 接口名 / 页面名）,
  reason:       禁止原因（现有依赖 / 合规约束 / 架构边界 / 历史数据风险）,
  consequence:  若违反此项会发生什么,
  adjacent_to:  与哪些改动点相邻（最容易在这些改动旁越界）,
  evidence:     依据来源（基线 PRD 章节 / 用户澄清说明）
}
```

**注意**：禁止改动项与改动点是并列关系，都在草案中独立输出。在 Story 的"改动范围→不涉及"中引用相关禁止项编号。

### 4.4 验收标准（AcceptanceCriteria）

```
AcceptanceCriteria = {
  id:        验收标准编号（如 AC-001）,
  cp_ref:    关联改动点编号,
  type:      功能验证 / 数据验证 / 权限验证 / 集成验证 / 边界验证,
  given:     前置条件（系统处于什么状态，哪些数据已存在）,
  when:      触发动作（执行什么操作）,
  then:      期望结果（必须可以被精确断言，不能有主观词汇）,
  negative:  反例（哪种情况应该不通过，可空）
}
```

**then 的写法要求**：

正确示例：
- "页面显示字段`供应商名称`，值与实体 Supplier.name 一致"
- "返回 HTTP 200，响应体包含字段 order_no，类型为 string，不为空"
- "角色`采购员`看不到按钮`审批通过`，DOM 中不存在该元素"
- "数据库表 purchase_order 中存在字段 supplier_code，类型为 varchar(50)，可为空"

错误示例（不可接受）：
- "界面展示正确"（无法断言）
- "系统正常运行"（无法断言）
- "用户体验良好"（主观，无法断言）

## 五、执行步骤详解（How）

以下是 Skill 的完整执行逻辑。每一步有明确的输入、处理方法、暂停触发条件和输出。

---

### Step 1：解析业务需求，识别原子变化场景

**输入**：业务需求文字 / 业务方案

**处理方法**：

逐句阅读需求，寻找变化信号，将每个信号映射到以下原子场景清单中的对应类型，并直接引用触发该判断的需求原文作为 evidence。

**原子场景完整清单**（所有合法的原子场景均在此列，如遇清单外的变化类型须在输出中注明并暂停询问）：

*UI 类——交互层变化*

| 编号 | 名称 | 识别关键词 |
|---|---|---|
| UI-01 | 操作入口新增 | 新增按钮、新增菜单项、新增 Tab、新增操作链接 |
| UI-02 | 新增页面 / 弹窗 | 新增页面、新增弹窗、新增抽屉、新增表单面板 |
| UI-03 | 已有页面新增字段展示 | 列表加字段、详情页加字段、表格加列 |
| UI-04 | 字段编辑能力变化 | 只读变可编辑、加必填校验、取消必填 |
| UI-05 | 界面流程步骤调整 | 新增审批步骤、跳过某步骤、调整提交流程 |
| UI-06 | 字段显隐 / 联动规则变化 | 条件显示字段、联动带出值、动态必填 |
| UI-07 | 操作入口变更 / 移除 | 按钮改名、按钮灰化条件变化、移除按钮 |
| UI-08 | 页面 / 模块整体删除 | 下线某功能页面、移除某模块 |

*DA 类——数据层变化*

| 编号 | 名称 | 识别关键词 |
|---|---|---|
| DA-01 | 现有实体新增字段 | 实体加字段、表加列、对象加属性 |
| DA-02 | 字段约束 / 类型变化 | 改字段长度、改枚举值、加默认值、改必填性 |
| DA-03 | 字段语义 / 赋值规则变化 | 字段含义调整、计算方式变化、来源变化 |
| DA-04 | 新增独立实体 | 新增业务对象、新增数据表、新增逻辑实体 |
| DA-05 | 实体关系变化 | 实体间关联关系调整、1:N 变 N:M |
| DA-06 | 实体状态流转变化 | 新增状态、删除状态、状态转换条件变化 |
| DA-07 | 历史数据处理 | 历史数据补填、数据迁移、存量数据默认值 |
| DA-08 | 数据删除 / 归档规则 | 数据保留策略、清理规则、归档触发条件 |

*LG 类——逻辑层变化*

| 编号 | 名称 | 识别关键词 |
|---|---|---|
| LG-01 | 新增独立功能模块 | 新增一个完整功能、新增一个独立能力 |
| LG-02 | 现有功能规则变化 | 校验规则变化、计算逻辑变化、处理方式变化 |
| LG-03 | 权限规则变化 | 角色可见性变化、操作权限变化、数据权限变化 |
| LG-04 | 通知 / 消息规则变化 | 新增通知、修改通知触发条件、修改通知内容 |
| LG-05 | 批量能力新增 | 批量导入、批量导出、批量处理、批量删除 |
| LG-06 | 配置项变化 | 新增可配置项、修改配置项、删除配置项 |

*PR 类——流程层变化*

| 编号 | 名称 | 识别关键词 |
|---|---|---|
| PR-01 | 新增端到端场景 | 新增业务流程、新增完整操作链路 |
| PR-02 | 现有场景步骤变化 | 流程步骤增减、主流程调整、异常分支变化 |
| PR-03 | 场景角色职责变化 | 某步骤执行者变化、审批人变化 |

*IN 类——集成层变化*

| 编号 | 名称 | 识别关键词 |
|---|---|---|
| IN-01 | 新增外部系统集成 | 对接新系统、新增接口、新增数据同步 |
| IN-02 | 现有接口契约变化 | 接口字段变化、入参出参调整、SLA 变化 |
| IN-03 | 集成移除 | 停用某接口、断开某外部系统依赖 |

*NF 类——质量层变化*

| 编号 | 名称 | 识别关键词 |
|---|---|---|
| NF-01 | 性能 / 并发指标变化 | 响应时间要求、并发量、数据量要求 |
| NF-02 | 安全 / 合规变化 | 数据脱敏、加密、审计日志、合规约束 |
| NF-03 | 可用性 / 容灾变化 | SLA、故障恢复、降级策略 |
| NF-04 | 埋点 / 监控变化 | 新增埋点、修改监控指标 |
| NF-05 | 可维护性变化 | 日志要求、运维操作、诊断能力 |

**Step 1 暂停触发条件**：

- 同一段需求文字可以合理对应两个以上不同原子场景，无法区分 → 暂停询问
- 识别出的场景置信度为"低" → 暂停询问（可与其他低置信度问题合并后一次性询问）
- 需求中有明确变化信号但场景类型超出清单范围 → 暂停询问

**输出**：AtomicScenario 列表

---

| IN-03 | 集成设计 | 应用架构、功能特性 |
| NF-01 | 非功能需求 | 应用架构、集成设计 |
| NF-02 | 非功能需求 | 权限设计、信息架构、集成设计 |
| NF-03 | 非功能需求 | 应用架构、集成设计、配置设计 |
| NF-04 | 非功能需求 | 功能特性 |
| NF-05 | 非功能需求 | 配置设计 |

注意：Story 设计是所有改动的最终收口，每个有效改动点都会生成对应 Story，在此不单独列入映射表。

**Step 2 暂停触发条件**：

"需验证"要素需要在基线 PRD 中查找对应章节。若基线 PRD 中完全没有该要素的章节（如无权限设计章节），无法判断是否影响 → 暂停询问。

**输出**：每个要素对应"必然影响 / 需验证 / 不影响"的初始判断，带上来源场景编号

---

### Step 3：执行依赖传导规则

**输入**：Step 2 的要素初始判断结果

**处理目的**：PRD 各要素之间存在上下游依赖关系。当某个要素发生"新增"类变化时，其上游来源要素也可能需要同步更新。Step 2 的映射表只覆盖了"原子场景 → 要素"的直接关系，这一步补充"要素 → 上游要素"的间接关系。

**处理方法**：

遍历 Step 2 的结果，逐条检查以下传导规则。凡命中规则的，将对应要素加入受影响清单，标注 trigger_type 为"依赖传导（规则 T-xx）"。

**传导规则 T-01：功能特性新增 → 应用架构必然影响**
- 触发条件：任意改动点的动作类型为"功能特性：新增"
- 原因：每个功能特性必须挂靠在应用架构的某个子特性节点下。新增功能特性意味着要么新增子特性，要么扩展现有子特性的范围，两种情况都涉及应用架构。
- 后续处理：在 Step 4 中回答——基线是否有子特性可承接本次新增的功能特性？有则应用架构"修改"，无则应用架构"新增子特性"。

**传导规则 T-02：功能特性.实体操作说明变化 → 信息架构需验证**
- 触发条件：功能特性的实体操作说明有新增或修改
- 原因：实体操作说明描述的是对信息架构中实体的 CRUD 操作，操作说明变化可能意味着字段或关系需要同步调整。
- 后续处理：检查操作涉及的字段和关系是否已在基线实体中存在。

**传导规则 T-03：场景解决方案新增 → 应用架构需验证**
- 触发条件：场景解决方案中新增了场景或步骤
- 原因：场景步骤需要子特性作为执行载体，新场景可能引用了尚未在架构中定义的子特性。
- 后续处理：检查新场景每个步骤是否有对应子特性承接。

**传导规则 T-04：新增页面 → 信息架构需验证**
- 触发条件：界面原型新增了独立页面（UI-02 触发）
- 原因：新页面展示或录入的字段必须有数据来源，需确认字段是否已在基线实体中存在。
- 后续处理：对页面上每个字段，在基线实体中核查是否已有对应字段。

**传导规则 T-05：新增页面 → Pageflow 必然影响**
- 触发条件：界面原型新增了独立页面（UI-02 触发）
- 原因：新页面必须有入口（从哪里跳进来）和出口（完成后去哪里），否则用户无法访问。
- 后续处理：明确新页面的入口触发点和操作完成后的跳转目标，更新 Pageflow。

**传导规则 T-06：页面删除 → 应用架构需验证**
- 触发条件：界面原型有页面整体删除（UI-08 触发）
- 原因：若被删页面是某个子特性的唯一 UI 载体，则该子特性在产品上实际已废弃，应用架构子特性树需同步更新。
- 后续处理：检查被删页面对应的子特性是否还有其他 UI 入口，如无则标记废弃。

**输出**：补充了传导触发要素的完整受影响要素清单，每个要素标注触发类型

---

### Step 4：对照基线 PRD 确认改动点，识别禁止改动项

**输入**：Step 3 的受影响要素清单 + 基线 PRD 文档

**处理方法**：

对每个受影响要素，在基线 PRD 中找到对应章节，阅读现有内容，分析本次变化需要改什么，生成 ChangePoint 对象；同时识别每个改动点相邻的禁止改动项，生成 ForbiddenItem 对象（独立列表）。

**"需验证"要素的处理**：

对 Step 2/3 中标注为"需验证"的要素，执行以下检查，根据结论决定保留或移除：

| 要素 | 关键检查问题 | 依据来源 |
|---|---|---|
| 信息架构 | 涉及的字段是否已在基线实体中存在？实体是否已有？ | 基线 PRD 实体详情章节 |
| 应用架构 | 是否有现有子特性可以承接新功能？是否有子特性需要废弃？ | 基线 PRD 子特性清单 |
| 权限设计 | 是否新增了角色可见 / 可操作的功能点？数据权限范围是否变化？ | 基线 PRD 权限矩阵 |
| 场景解决方案 | 端到端业务链路是否发生变化？ | 基线 PRD 场景清单 |
| 集成设计 | 是否涉及外部系统？是否改变了对外契约？ | 基线 PRD 集成点说明 |
| 配置设计 | 是否有参数需要运行时可配置？ | 业务需求描述 |
| 非功能需求 | 是否引入新的性能、安全、隐私约束？ | 业务需求描述 |

**防过度设计检查**（避免把小需求分析成大改动）：

- 新增按钮 ≠ 必然新增子特性（需判断是否有独立业务边界）
- 新增页面 ≠ 必然新增实体（页面可能展示已有实体数据）
- 表格加展示字段 ≠ 必然修改信息架构（字段可能已有）
- 字段入库 ≠ 必然新增端到端场景
- 新字段 ≠ 必然修改集成设计（只有需要对外暴露时才影响）

**每个 PRD 要素的改动分析要点**：

**应用架构**
- 关键问题：新功能挂靠哪个子特性？是否需要新增子特性节点？是否有子特性需要废弃？
- 分析内容：子特性新增、范围扩展、废弃标记
- 常见动作：修改（扩展现有子特性范围）/ 新增（添加新子特性节点）/ 废弃

**界面原型**
- 关键问题：哪个页面改了什么控件？新页面的入口和出口是什么？
- 分析内容：页面、按钮、字段、弹窗、Pageflow 的具体变化
- 注意：新增页面时必须同步更新 Pageflow（T-05 规则）

**信息架构**
- 关键问题：字段是否已存在？实体是否已存在？历史数据如何处理？
- 分析内容：字段定义（名称、类型、必填性、枚举值）、实体结构、ER 关系、数据样例
- 注意：新增字段必须说明历史数据的处理策略（默认值或迁移方案）

**功能特性**
- 关键问题：是新增功能特性还是修改已有功能特性？操作步骤、业务规则、实体操作说明是否变化？
- 分析内容：UIUX 操作说明、实体操作说明、业务规则、校验逻辑、异常处理
- 注意：功能特性"新增"时必须触发 T-01 检查

**权限设计**
- 关键问题：谁能看这个功能？谁能操作？数据权限范围是否变化？
- 分析内容：角色权限矩阵、按钮权限、数据可见范围的具体变化

**集成设计**
- 关键问题：是否涉及外部系统？接口入参或出参是否变化？
- 分析内容：接口字段、数据映射、调用时机、异常处理

**配置设计**
- 关键问题：业务规则是否需要参数化？是否有运行时可调整的配置项？
- 分析内容：配置项名称、类型、默认值、作用域

**场景解决方案**
- 关键问题：端到端业务链路是否变化？是否新增场景或修改现有场景步骤？
- 分析内容：场景名称、步骤描述、角色、数据流向

**非功能需求**
- 关键问题：是否引入新的性能、安全、隐私、审计要求？
- 分析内容：具体指标或约束的变化

**禁止改动项的识别范围**：

每个改动点分析完成后，检查以下类型的对象是否需要列为禁止项：

1. **现有接口契约**：本次改动涉及接口，但接口已有其他调用方（需依据：基线 PRD 集成点说明中有记录）
2. **实体主键和唯一约束**：本次改动涉及的实体中，主键和业务唯一键禁止修改
3. **外部系统依赖字段**：若某字段有外部系统订阅（需依据：基线 PRD 集成设计中有记录，否则须询问用户）
4. **范围外的相邻代码区域**：改动点 in_scope 之外但物理临近的功能区域
5. **架构边界**：本次明确不涉及的模块、服务、表

**最低密度要求**：每个 ChangePoint 至少对应一条 ForbiddenItem，覆盖其最近的高风险相邻对象。

**Step 4 暂停触发条件**：

- ChangePoint 的 target_state 无法从需求原文中确定（如需求只说"加字段"但未说字段名、类型、必填性）→ 暂停询问
- 历史数据处理策略不明确 → 暂停询问
- 禁止改动项需要外部系统依赖知识，但基线 PRD 无记录 → 暂停询问
- 信息架构字段已存在但定义与需求描述有语义出入 → 暂停询问

**输出**：ChangePoint 列表（含 baseline_state 和 target_state）+ ForbiddenItem 独立列表

---

### Step 5：拆分增量 Story，编写结构化验收标准

**输入**：Step 4 的 ChangePoint 列表

**处理方法**：

按 INVEST 原则拆分 Story：每个 Story 应满足——
- **I（Independent）**：Story 之间尽量相互独立，可以单独开发和验收
- **N（Negotiable）**：Story 描述的是"做什么"而非"怎么做"
- **V（Valuable）**：每个 Story 对用户或系统有可感知的价值
- **E（Estimable）**：Story 粒度应可以被评估工作量（通常1-3天）
- **S（Small）**：一个 Story 不超过一个人一个迭代完成
- **T（Testable）**：有明确可验证的验收标准

**验收标准必须覆盖的类型**：

- 所有"界面原型"改动：至少一条功能验证（字段正确展示）
- 所有"信息架构"改动：至少一条数据验证（字段正确存储）
- 所有"权限设计"改动：至少一条权限验证（角色可见性正确）
- 所有"集成设计"改动：至少一条集成验证（接口返回正确）
- 涉及边界条件（必填、长度限制、枚举值）的改动：至少一条边界验证

**then 编写原则**：
- 描述系统的可观测状态，而非操作过程
- 精确到字段名、状态值、HTTP 状态码等可断言的具体值
- 不使用"正确"、"成功"、"正常"等主观词汇，除非紧跟具体可验证的状态

**Story 格式**：

```markdown
## Story [编号]：[Story 名称]

**来源**：ChangePoint [CP-xxx]，场景 [UI-xx / DA-xx ...]

**用户故事**：
作为 [角色]，我希望 [做什么]，以便 [达到什么目的]。

**改动范围**：
- 涉及：[明确列出改动对象]
- 不涉及：[引用相关 ForbiddenItem 编号及对象名]

**详细说明**：
[基于 ChangePoint 的 target_state 展开描述]

**验收标准**：
- AC-[编号]（[类型]）
  - Given：[前置条件]
  - When：[触发动作]
  - Then：[期望结果]
  - Negative：[反例，可空]

**关联 PRD 章节**：[对应 PRD 要素章节引用]
```

**输出**：增量 Story 列表

## 九、完整执行案例

以下两个案例完整演示了 Skill 的执行过程，包括澄清暂停的触发和处理方式。

---

### 案例 A：业务需求信息不完整，需要多次澄清

**场景背景**：用户提交如下业务需求，并附上了基线 PRD。

> **业务需求原文**：
> "在采购单页面增加供应商指定功能，采购员可以录入供应商相关信息并保存。历史采购单也需要处理。"

**基线 PRD 摘录**（用户提供，以下是与本次分析相关的部分）：
> - 应用架构 §2.3：子特性清单包含"采购单创建"、"采购单查询"、"采购单审批"，无"供应商指定"相关子特性
> - 界面原型 §3.1：采购单列表页，列含：采购单号、状态、金额、创建人、创建时间；操作列含：查看、编辑、删除
> - 信息架构 §4.2：PurchaseOrder 实体字段：order_no（主键）、status、amount、creator_id、created_at
> - 权限设计 §6.1：角色清单包含采购员、采购主管、财务；**权限矩阵章节标注"待完善"**
> - 集成设计 §7.1：采购单列表接口 GET /api/purchase-orders，供外部报表系统调用，出参包含全部 PurchaseOrder 字段

---

**🤖 Skill 执行开始**

**Step 1：识别原子变化场景**

阅读需求原文，提取变化信号：

- "增加供应商指定功能" → 有"增加功能"信号，但不清楚是新增按钮进入弹窗，还是在现有编辑页直接加字段，两种解读对应不同原子场景。→ 置信度：低
- "录入供应商相关信息" → 有录入动作，说明存在录入界面，但字段不明确。→ 信息不足
- "历史采购单也需要处理" → 对应 DA-07（历史数据处理），置信度高，但处理方式不明确。

识别到低置信度问题，触发暂停。

---

> ⏸ **分析暂停 — 需要澄清以下问题，才能继续 Step 1**
>
> **Q1：供应商指定功能的入口形式是什么？**
> 背景：需求说"增加供应商指定功能"，可以理解为（a）在采购单列表页加一个"指定供应商"按钮，点击后弹窗录入；或（b）在采购单编辑页直接新增供应商相关字段。两种方式对应不同的原子场景，分析结论不同，无法推断。
>
> **Q2：需要录入哪些供应商信息？请列出字段名称、类型和必填性。**
> 背景：需求提到"录入供应商相关信息"，但未说明具体字段。字段定义直接决定信息架构是否需要变更，以及变更的具体内容，无法推断。
