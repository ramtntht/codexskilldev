# m-prd-tp-feature — 功能特性

> 以应用架构章节的子特性清单为基础，**不重新生成编号**，为每个子特性补充 UIUX 操作说明、实体操作说明、集成点说明、业务规则和 BDD 格式验收标准。

---

## 目标

**目标说明**

功能特性是 PRD 最核心的执行规格层，将应用架构的"子特性是什么"扩展为"子特性怎么做"。每个子特性对应：用户如何操作（UIUX）、数据如何变化（实体操作）、外部系统如何配合（集成点）、规则约束是什么（业务规则）、如何验收（BDD AC）。

**重要约束**：子特性编号（FR-{特性分类}-{特性}-{序号}）由应用架构章节唯一定义，本章节**只引用，不重新生成**。

**输出物**

- 特性分类总览表格（特性分类 | 特性名称 | 包含子特性编号范围）
- **每个子特性**的详细描述（FR 编号 + 名称 + UIUX 操作步骤 + 实体操作列表 + 集成点说明 + 业务规则列表 + BDD 验收标准）

**成功标准**

- 所有 FR 编号与应用架构章节子特性清单完全一致，无遗漏和新增
- **应用架构中有多少个子特性，本章节就有多少个子特性的详细规格**，数量必须完全对应
- 每个子特性必须包含5个必填项：UIUX操作说明（≥3步）、实体操作说明、集成点说明（无则写"无外部集成"）、业务规则列表、BDD 验收标准（≥1条）
- 每个子特性至少有 1 条 BDD 格式验收标准（`ACn: Given / When / Then`）
- 业务规则直接引用 FE 活动明细的规则编号（BR-xxx），有明确规则编号

## 约束

### 格式规范

| standard_id | 规范说明 |
|-------------|---------|
| —（暂无格式规范引用） | 验收标准使用 BDD 格式（约束在设计约束中定义）|

### 设计约束

| 约束编号 | 级别 | 规则 | 验证方法 |
|----------|------|------|---------|
| `DC-FEAT-001` | `MUST` | 子特性编号必须直接引用应用架构章节的 FR 编号，禁止重新生成或修改编号 | 对照应用架构章节子特性清单，检查本章节 FR 编号是否完全一致 |
| `DC-FEAT-002` | `MUST` | **本章节详细规格的子特性总数，必须等于应用架构章节子特性清单的总数**，不得遗漏任何一个子特性 | 统计应用架构章节子特性总数N，检查本章节是否有N个带有完整规格（含UIUX/实体/集成/规则/AC）的子特性详细描述章节 |
| `DC-FEAT-003` | `MUST` | 每个子特性必须包含以下5个必填规格项，缺少任一项均视为该子特性规格不完整：(1) UIUX操作说明（≥3步）(2) 实体操作说明表格 (3) 集成点说明（无集成时写"无外部集成"，不得留空）(4) 业务规则列表（引用BR编号）(5) BDD格式验收标准（≥1条AC） | 检查每个子特性详细描述是否包含5个规格项标题和内容 |
| `DC-FEAT-004` | `MUST` | 每个子特性必须有至少 1 条 BDD 格式验收标准，格式为：`ACn: Given [前提] / When [触发] / Then [预期]` | 检查每个 FR 是否存在 AC 字段，且格式符合 BDD 结构 |
| `DC-FEAT-005` | `MUST` | 业务规则编号必须引用 FE 活动明细中的规则编号（BR-xxx），禁止自行创造规则编号 | 检查 BR 编号是否与 FE 原文一致 |
| `DC-FEAT-006` | `SHOULD` | UIUX 操作步骤应以用户角度描述（"用户点击…" "系统跳转…"），不少于 3 步 | 检查操作步骤数量和描述视角 |

## 执行步骤

**Step 1：引用应用架构的子特性清单，建立特性分类总览** `[自动]`

直接读取 PRD 应用架构章节（已完成）的子特性清单，按特性分类归组，生成特性分类总览表格，说明每个特性分类包含的子特性编号范围（如 FR-01-01-001 ~ FR-01-02-003）。

在此记录子特性总数 `N = {总数}`，作为后续完整性验证的基准。

---

**Step 2：逐一为每个子特性生成完整规格** `[交互]`

> **强制完整遍历约束**：必须为应用架构子特性清单中的**每一个**子特性生成完整的5项规格（UIUX/实体/集成/规则/AC）。子特性数量无论多少（哪怕超过20个），都必须全部完成，不得以"其余子特性规格类似"、"以此类推"等理由跳过或合并。

执行以下循环：

FOR EACH sub_feature IN app_architecture.sub_features_list:
  1. 生成 UIUX 操作说明（从FE活动明细.操作内容字段提取，≥3步，用户视角描述）
  2. 生成 实体操作说明表格（从FE活动明细.输出结果字段推导，引用信息架构实体名称）
  3. 生成 集成点说明（从FE外部依赖和应用架构系统边界识别；若无外部集成，明确写"无外部集成"）
  4. 生成 业务规则列表（引用FE活动明细.业务规则字段，保留BR编号）
  5. 生成 BDD验收标准（基于业务规则和输出结果推导，至少1条Happy Path AC，建议加1条Error Path AC）
END FOR


对于包含 `[交互]` 步骤的子特性（验收标准确认），在所有子特性规格初稿生成后，**批量**展示所有子特性的验收标准草稿，统一进行一次确认，避免每个子特性都打断执行。

> **交互提示**：展示所有子特性的验收标准汇总，询问用户："以上{N}个子特性的验收标准是否完整？是否有遗漏的验收场景或需要调整的条目？"

---

**Step 3：完整性自验证** `[自动]`

> **此步骤强制执行，不得跳过。**

1. 统计本章节已生成详细规格的子特性数量 `M`。
2. 对照 Step 1 记录的子特性总数 `N`。
3. 若 `M < N`：
   - 列出缺失的子特性编号（在 `N` 中但不在 `M` 中的 FR 编号）
   - 立即补充缺失子特性的完整规格，直到 `M == N`
   - 不得跳过此补充操作进入 Phase 5（质量验证）
4. 若 `M == N`：输出验证通过信息：`✅ 子特性完整性验证通过：已生成 {N}/{N} 个子特性详细规格`
